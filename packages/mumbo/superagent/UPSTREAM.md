## S3: delivery policy

`Policy.delivers(trigger)` in `src/core/ports.ts` decides whether a Trigger may reach a Ticket as an Input. Upstream delivers every Trigger on a subscribed Thread, whoever sent it.

- `src/policy.ts`: `settingsPolicy` delivers through `deliverable(settings, trigger)`. A person's Trigger is delivered only when `allowedSender` finds the sender on the Source's allowed list. A non-human Trigger is delivered only when `listedBot` finds it on the Source's bot list, or when it is GitHub CI: `source === 'github'`, an empty actor id and `meta.ci === true`, which `ciTrigger` (a PR's CI) and `branchCiTrigger` (default-branch CI) set. Every other senderless Trigger, such as a Feishu system, anonymous or id-less app message, is withheld and goes to Eval.
- `src/core/intake.ts`: subscription fan-out reaches no Ticket for a Trigger the Policy does not deliver. No Ticket decides that Trigger, so it is queued for Eval and resumes no ended Ticket.
- `src/core/tickets.ts`: `attachable` refuses such a Trigger with `notAdmissible`, reason `not_a_member` for a person and `not_human` for a bot. The `Engine.attach` `@throws` in `src/core/engine.ts` names this refusal.
- `src/executor/dsh.ts`: a delivered Trigger's `replies_to` preview, pushed to the worker, shows the message it answers only when `deliverable` would deliver that message.
- A merged pull request still ends the Tickets that follow it through PR polling, whoever merged it, so the merge bot needs no allowed-list entry.
- Prompts, each pinned in `tests/cards.spec.ts`:
  - `prompts/subscriptions.md` tells both roles that only an allowed person, a listed bot or CI reaches a Ticket, by subscription or by attach, and that an allowed sender's message resumes an ended Ticket.
  - `prompts/orchestrator.md` tells the main Session that messages on a subscribed thread from an allowlisted person, a listed bot or senderless CI go to the workers, and that an allowlisted person's message resumes an ended Ticket.
  - `prompts/dispatch.md` says CI, and review feedback from allowed senders and listed bots, reaches the worker directly.
- The bot-list hints of the GitHub and Feishu Sources (`src/sources/github.ts`, `src/sources/feishu.ts`) say a listed bot's messages on a subscribed thread also go straight to the tickets' Executors.
- `docs/001-domain.md` (fan-out "with no check of who sent it") and `docs/002-authorization.md` (every message on a subscribed Thread reaches its Tickets; resume "regardless of who sent it") are upstream prose this entry supersedes on who reaches a Ticket.
- Known limits:
  - `delivers` gates only what reaches a Ticket as an Input. A worker that reads a pull request or chat thread itself still sees the text of senders who are not on the allowed list. So does the `trigger/` resource it reads, whose `around` neighbours list every Trigger on a subscribed thread (`reached`).

## S7: GitHub App mode

Upstream's agent is a GitHub user account: setup reads `gh api user` and requires `permissions.push`, and the GitHub Source polls the account's notifications. A GitHub App installation token answers 403 for `/user` and `/notifications` and reports no `permissions` on `repos/<owner>/<name>`. App mode lets the agent act as an App's bot, such as `mumbo-bot[bot]`, through a CLI whose requests carry such a token. Written by task G1b.

- `src/deployment.ts`: the optional `githubApp: { login, userId }` key, where `login` matches `^[A-Za-z0-9-]+\[bot\]$` and `userId` is a positive integer; a malformed value fails at load. The object schema is wrapped in a union so an absent key stays absent instead of taking the object's implicit `{}` default. `Machine.githubApp` (and so `Deployment.githubApp`) carries it through `machineOf`; it is not volatile, so a change remounts the plugin. With it, `resolveDeployment` makes no `api user` probe: the login is `githubApp.login` and the commit email `<userId>+<login>@users.noreply.github.com`. The repository unset, CLI unset and CLI missing checks stay, and so does the `repos/<repository>` probe, which proves the CLI reaches GitHub and may read the repository; its failure is `repositoryUnreadable` naming the bot login. `push: true` and `push: null` (not reported) pass, and `push: false` is `repositoryReadOnly`. Without `githubApp` setup is unchanged.
- `src/sources/github-trigger.ts`: `mentions()` matches a `<slug>[bot]` login as `@<slug>`, the form people write, and as `@<slug>[bot]`; `@<slug>2` and `@<slug>[bot]x` do not match. A user login matches as before. In both modes it ignores fenced code blocks, inline code spans and HTML comments, which GitHub does not render as mentions, so a user account's mention there no longer addresses it either; a quoted mention still counts. It finds them close to CommonMark, after normalizing `\r\n` and `\r` to `\n`. Blocks first, whichever starts first: a fence is a line of three or more backticks or tildes indented up to three spaces (a backtick fence's info string has no backtick), closed by a line of at least as many of the same character or by the end of the text; an HTML comment that starts a line runs through `-->` or to the end. Then inline text, left to right: an escaped backslash or backtick, a closed HTML comment, or a code span, a backtick run closed by the next run of the same length that crosses no blank line and no line that starts an ATX heading, a quote or a list item; a backslash inside a span is part of it. An unclosed HTML comment inside a line hides nothing. Indented code blocks are not recognized, and a span opened right after an escaped backtick is missed. Every addressed Trigger goes through it. Author checks (`isHumanLogin`, the agent's own items in `src/sources/github.ts`, `agentPull` in `src/sources/github-pull.ts`, the agent's own comments in `src/sources/github-channel.ts`) compare the full `<slug>[bot]`, which GitHub returns as `user.login`, and are unchanged.
- `src/sources/github.ts`:
  - `pollRound` makes no notifications request in App mode. Its interval is the configured `pollSeconds`, and its health detail reads `repository streams read` instead of a notification count.
  - `pollRepository` reads the `issues`, `comments` and `review-comments` streams every round in App mode, whatever the receive switches, and resets no stream.
  - `readStream` keeps its cursor, ETag and per-kind `started` records as before. In App mode it adds a `started.app` entry, the first App-mode round that read the stream, so nothing older is received through the App-mode rules and the switch to App mode replays nothing, and a `read` entry, the start of the stream's last read. The ETag is sent only once every current kind has a start, so a 304 after a switch from user mode cannot keep `started.app` unwritten while a new mention ages past it. A round reads one page of 100, so `read` advances only after a page that was not full; after a full page it keeps its value, so an item a later round lists from beyond that page still counts as new. The cursor steps to five seconds before the newest listed item; when a full page falls entirely within those five seconds, it steps to the newest item itself instead, which GitHub's inclusive `since` lists again, so the stream does not list the same page forever. More than 100 items updated in the same second still hold it until one of them is updated again.
  - Before `ctx.receive`, a new Issue or pull request is received when its receive switch took it in (as before), or when its body mentions the agent and it was created since `cursorAt(read)`. The stream's cursor stays five seconds before its newest item, so in a quiet repository an edited Issue stays after the cursor; only `read` keeps a mention added by editing the body, which would be credited to the body's author, from being received, as `readNotified` does for a user account.
  - A comment or review comment is received when `observeComments` took it in (as before), when it mentions the agent, or when a Ticket subscribes to its Thread `github:<number>` and that Thread is `polled` or the comment was created since `cursorAt(read)`; an edit of an old comment on a Thread whose Tickets are past the polling horizon is not received. Once a new comment makes such a Thread polled again, `pollThread` reads everything since polling stopped, including edits and reviews. Anything else becomes no Trigger.
  - `startThread` sets `KV.github.cursor(number)` to the creation time of each Issue or pull request the `issues` stream newly stores in App mode, through a switch or a mention, and, for each mention in a comment received through the App-mode rules, to the comment's creation when the comment is new since the last read, or to the edit (its `updated_at`) when an older comment was edited to add the mention, so such an edit reads none of the replies before it. Once the Ticket subscribes, `pollThread` reads from there, so replies posted before the subscription, which the stream dropped, become Triggers; Trigger IDs absorb the item read again. It replaces an existing position only when the Thread was idle before the item arrived (`idle`: no Trigger pending or in an Eval, and no Ticket subscription that is `polled`). A new Ticket on an old Thread then does not read the replies of an earlier request that started none, while a second mention during the first one's Eval keeps the earlier position, so the replies between them are read.
  - The agent's own items are skipped by login as before, except that the agent's own open pull request from the `issues` stream is read with `pull()` first, so `observePull` binds it to the open Ticket on its branch, as its notification does for a user account, and, while no Ticket subscribes to its Thread (checked before the read), its Thread's read position starts at the pull request's creation, replacing a later position a mention set, so reviewer comments the stream dropped before the bind are read. Once a Ticket subscribes, including one that followed the pull request before, its position is kept. A failed read is recorded as for a ticket's pull request and fails the round.
  - `pollTicketPulls` (ticket pull requests and their CI), `pollThreads` (subscribed Threads, reviews included) and `pollBranchCi` (default-branch CI under `observeCi`) are unchanged.
  - Wording that held only for a user account and its notifications: the kind's `description` adds that a GitHub App receives what mentions it instead of notifications; the `repository` hint says the Source receives the repository's discussion and that saving checks the agent account's access; the `cli` hint names a gh whose requests act as the App's bot as the alternative to a signed-in wrapper; the `DSH_SUPERAGENT_GITHUB_ACCOUNT` description says gh acts as the account instead of being signed in to it.
- `src/kv.ts`: the stream record has the optional `read`, and the `github` record's comment names it and the App-mode start time.
- Ruling on the spec's third Trigger condition, a comment from an allowlisted sender: App mode does not add it.
