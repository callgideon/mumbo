# mumbo boxes: runbook

One section per alarm in `prod/ops.tf` (alarm name `mumbo-boxes-<section>`), then routine operations. Commands run from `deploy/boxes/prod` with AWS credentials for account 641134885443. Logs: CloudWatch groups `/mumbo-boxes/{edge,api,client-proxy,setup}`, and `/mumbo-boxes/nodes` with streams `<instance>/orchestrator`, `<instance>/lifecycle` (drain) and `<instance>/boot`; node memory and disk metrics in namespace `mumbo/boxes/nodes`. A new node's orchestrator restarts 3–5 times at first boot (root cgroup race) before it serves; that is expected.

## Alarms
Every alarm and the `edge-deploy-failed` notice go to the SNS topic `mumbo-boxes-alarms`. `ops_alert_email` in `prod/terraform.tfvars` (the founder, `hi@mumbo.si`) subscribes one address by email. After the apply that adds or changes it, AWS mails that address a confirmation link, which must be clicked once; until then nothing is delivered. Check:
```sh
aws sns list-subscriptions-by-topic --topic-arn "$(terraform -chdir=deploy/boxes/prod output -raw alarm_topic)" --query 'Subscriptions[].[Protocol,Endpoint,SubscriptionArn]' --output text
```
`PendingConfirmation` in the last column means the link has not been clicked.

### edge-backup-failed
A box backup to S3 failed; the sweep retries in 5 minutes. Find the box with `aws logs filter-log-events --log-group-name /mumbo-boxes/edge --filter-pattern '{ $.msg = "backup failed" }'`. Repeated failures for one box usually mean a full disk in the box or a stopped box; repeated failures for every box mean the edge role lost S3 access.

### edge-restore-failed
Restoring a person's or project's backup into a new box failed part way (`{ $.msg = "restore" && $.ok IS FALSE }`, level error), or the version an operator's restore record names could not be read (`{ $.msg = "restore version unknown" }`, level error, with `versionId`, `error` and S3's HTTP `status`; no box was created). The edge dropped any box, so nothing backs up a partly restored box over `latest.tar.gz`. The person's page says "Your computer could not be restored from its backup. The operator has been alerted." and keeps reloading, and each reload after a failure tries the restore again. A failure on every attempt means the archive itself is bad (truncated, or a member tar cannot extract): restore an older version as below.
`restore version unknown` never falls back to `latest.tar.gz`, and the record stays, so every visit fails the same way until the record is fixed or cleared with `restore-version.mjs` (below). `status` 404: the version is gone (noncurrent versions expire after 30 days) or never existed; 405: it is a delete marker; 400: a malformed id; 403: the edge role lacks `s3:GetObjectVersion`, so the Terraform apply of B30 is missing. No `status`, with `error` "the record has no versionId": the record is malformed; clear it.

### Restore an older S3 version
The backup bucket is versioned and keeps noncurrent versions for 30 days. Only the edge role may decrypt the archives (the bucket's KMS key policy), so an operator can neither open nor copy a version. Instead, a one-shot restore record in the edge's Redis (`restore:<principal>` = `{ versionId, at }`) makes the box's next creation restore that version. That box's first backup, which the next sweep takes (about a minute), writes it back as a new `latest.tar.gz`, and the edge then deletes the record; a box lost before that backup is recreated from the same version. Nothing is deleted: every newer version stays until it expires. Preconditions: the live `edge_tag` is B30 or later, and the Terraform apply that gives the edge role `s3:GetObjectVersion` (`prod/modules/edge/edge.tf`) has run before the first versioned restore; without it the restore fails with `restore version unknown`, `status` 403. On an edge before B30, use the fallback below.
1. Open the tunnels and set the variables of "Offboarding a person" step 4 (`npm ci --prefix deploy/boxes/edge` once). The E2B tunnel and `E2B_API_KEY` only let the script list the box; without them, or when E2B fails, it prints `box: not checked` and still lists and writes the record. The principal is the email in lower case, or `project:<id>` for a project box.
2. List the versions, the pending record and the box:
   ```sh
   node deploy/boxes/edge/restore-version.mjs <principal>
   ```
   Each line is a version of `users/<sha256 of the principal>/latest.tar.gz`, newest first: time, size, version id, and `latest` on the current one; delete markers are shown as such. Choose the newest version from before the problem. Since nobody but the edge can open an archive, choose by time and size: a version far smaller than its neighbours is a truncated one.
3. Set the record (the principal repeated, as confirmation). The script refuses an id that is not a version of exactly that key, or is a delete marker. A dry run first, with the version id alone, checks it and changes nothing:
   ```sh
   node deploy/boxes/edge/restore-version.mjs <principal> <version id>
   node deploy/boxes/edge/restore-version.mjs <principal> <version id> --set <principal>
   ```
   `--clear <principal>` instead of `<version id> --set <principal>` removes a pending record. Setting again replaces it.
4. The record takes effect only when the box is next created. If the `--set` run printed a running or paused box, kill it as in "Moving a box to a new template build" step 2; the script lists the box after writing the record, so a box created meanwhile shows too. If it printed `box: not checked`, find the principal's box in that section's listing. Work since that box's last backup is lost; to keep it in a version the person can return to, do that section's step 1 first.
5. The person's next visit (a project box: a member opening the project) creates a box and restores the chosen version. Confirm with `aws logs filter-log-events --log-group-name /mumbo-boxes/edge --start-time $(( ($(date +%s) - 1800) * 1000 )) --filter-pattern '{ $.msg = "restore" && $.ok IS TRUE && $.versionId = "<version id>" }' --query 'events[].message' --output text`, a line with the principal. After that box's first backup (about a minute later), `restore-version.mjs <principal>` shows `pending restore: none`; the versions after the chosen one stay listed until they expire. A failed restore keeps the record, and the next visit tries the same version ("edge-restore-failed"). If the person has visited but no such restore line appears, a box the edge was creating during step 3 is still running: rerun `restore-version.mjs <principal>` and kill the box it lists, as in step 4. Never leave a record pending: it applies at the box's next creation, whenever that comes (a failed resume, a lost node, a template move), and rolls the person back to that version; `--clear` a record no longer wanted.
6. `kill %1 %2` closes the tunnels.

**Fallback for an edge before B30: delete the newer versions.** Each delete is permanent: that archive, and the work it held, is gone. Use it only while the live edge cannot restore a version. Run from a shell with the production AWS credentials.
1. Make sure no box backs up over the key meanwhile. A box that is failing its restore is never backed up. A running box (the person wants older data back) is backed up every 10 minutes: ask the person to stop, then kill it as in "Moving a box to a new template build" step 2, and ask them not to open mumbo until step 4 is done.
2. Name the key: the email in lower case, or `project:<id>` for a project box.
   ```sh
   B=mumbo-boxes-backup-$(aws sts get-caller-identity --query Account --output text)
   K="users/$(printf %s '<email or project:id>' | sha256sum | cut -d' ' -f1)/latest.tar.gz"
   aws s3api list-object-versions --bucket "$B" --prefix "$K" --query "Versions[?Key=='$K'].[LastModified,Size,VersionId,IsLatest]" --output text | sort
   ```
3. Choose the newest version from before the problem, by time and size as above. Then delete every version newer than it, one by one with `aws s3api delete-object --bucket "$B" --key "$K" --version-id <newer version id>`. Each delete is permanent: that archive, and the work it held, is gone. Rerun the listing; the chosen version must now show `True` in the last column.
4. The person's next visit creates a box and restores it. Confirm with `aws logs filter-log-events --log-group-name /mumbo-boxes/edge --start-time $(( ($(date +%s) - 1800) * 1000 )) --filter-pattern '{ $.msg = "restore" && $.ok IS TRUE }' --query 'events[].message' --output text`, a line with their email. Everything after the chosen version's time is lost.

### edge-pause-failed
An idle box could not be paused. E2B's own timeout pauses it 15 minutes later regardless. A box E2B no longer has is dropped from the store automatically; anything else is retried on the next sweep.

### edge-errors
Unhandled edge errors (one log line each, with path and user). Read the lines; a burst after a deploy means roll back `edge_tag` in `terraform.tfvars` and apply.

### edge-deploy-failed
Not a CloudWatch alarm: the EventBridge rule `mumbo-boxes-edge-deploy-failed` sends ECS's `SERVICE_DEPLOYMENT_FAILED` event for the edge service to the alarm topic as one line of text (`mumbo-boxes edge deployment <id> failed at <time>: <reason>`), not alarm JSON. The deployment circuit breaker stopped the rollout and rolls the service back to the previous task definition, so the edge keeps serving the old image while `edge_tag` in `prod/terraform.tfvars` names the failed one. Handle it as in "Ship a new edge", step 6.

### edge-dropped-create
A replica died while restoring a new box; the box was killed and the next visit restores from the backup again. One is harmless. Several mean edge tasks are being killed mid-request: check `tasks-edge`.

### github-not-approved
The mumbo-bot App's installation refused a token because it has not accepted a permission the edge asks for; project boxes get 503 on GitHub and the approvals poller lists nothing. Fix it as in "GitHub: the agent is the mumbo-bot App" below.

### api-node-unhealthy
E2B marked a node unhealthy. Check the node: `aws ssm send-command` with `systemctl status e2b-orchestrator` and `journalctl -u e2b-orchestrator -n 100`. If it does not recover, replace it: `aws autoscaling terminate-instance-in-auto-scaling-group --instance-id <id> --no-should-decrement-desired-capacity`. Termination pauses its boxes first (`mumbo-drain`) and the boxes resume on other nodes.

### node-disk
The fullest node's root volume is over 75% used (CloudWatch agent `disk_used_percent` on `/`, namespace `mumbo/boxes/nodes`). Act before it fills: a node refuses a pause unless its disk can take the box's snapshot and keep 4096 MiB free (`PAUSE_ADMISSION_DISK_HEADROOM_MIB` in `prod/nodes/node.sh.tftpl`), so a full node can neither pause idle boxes nor drain. Find the node and what fills it:
```sh
aws cloudwatch get-metric-data --start-time $(date -u -d '-15 min' +%FT%TZ) --end-time $(date -u +%FT%TZ) --query 'MetricDataResults[].[Label,Values[0]]' --output text \
  --metric-data-queries '[{"Id":"d","Period":300,"Expression":"SELECT MAX(disk_used_percent) FROM SCHEMA(\"mumbo/boxes/nodes\", AutoScalingGroupName, InstanceId, device, fstype, path) WHERE path = '"'/'"' GROUP BY InstanceId"}]'
CMD=$(aws ssm send-command --instance-ids <instance id> --document-name AWS-RunShellScript --query Command.CommandId --output text \
  --parameters 'commands=["df -h /","du -xsh /orchestrator/* /var/lib/e2b/build-cache /var/log 2>/dev/null | sort -h | tail"]')
aws ssm get-command-invocation --command-id $CMD --instance-id <instance id> --query StandardOutputContent --output text
```
(`date -d` is GNU date; on macOS use `date -u -v-15M +%FT%TZ`.) `/orchestrator` holds the running boxes' disks and memory, the template cache and snapshots in transit; `/var/lib/e2b/build-cache` holds template build layers. Replace the node while it can still drain: `aws autoscaling terminate-instance-in-auto-scaling-group --instance-id <id> --no-should-decrement-desired-capacity`; its boxes pause and resume on the other nodes, and the replacement starts empty. If every node fills, the volume is too small for the boxes per node: raise `volume_size` ("Node disk size").

### edge-5xx
More than 20 edge 5xx in 5 minutes. 503s are capacity or a box starting; 502s are the edge or a box not answering. Check `unhealthy-*`, `tasks-*` and `nodes-below-min` first.

### nodes-below-min
Fewer sandbox nodes in service than `node_count`. Raising `node_count` raises this alarm until the new nodes are in service, which is expected. Read the ASG activities: `aws autoscaling describe-scaling-activities --auto-scaling-group-name mumbo-boxes-nodes --max-items 5`. A launch failure names its cause (capacity in the AZ, a bad launch template). The boot log is `/var/log/mumbo-node.log` and the console output.

### unhealthy-edge-user, unhealthy-edge-model, unhealthy-api-http, unhealthy-api-grpc, unhealthy-proxy
A load balancer target fails its health check. ECS replaces failing tasks; the alarm clears when the replacement passes. If it does not, read the service's log group.

### tasks-api, tasks-client-proxy, tasks-edge
A service runs fewer than two tasks. `aws ecs describe-services --cluster mumbo-boxes-e2b --services <name> --query 'services[0].events[:5]'` names the reason (image pull, secret access, failing health check, circuit-breaker rollback).

### memorydb-memory
E2B's Redis is over 75% memory. Losing keys kills running sandboxes (review B1), so scale before it fills: raise `node_type` of `module.cell_us_east_1.aws_memorydb_cluster.e2b` in `prod/modules/cell/data.tf` and apply (online).

### rds-cpu, rds-storage
Postgres is busy or short of space. Storage grows automatically up to 500 GB; CPU means resizing `instance_class` in `prod/modules/cell/data.tf` (Multi-AZ failover, about a minute).

## Operations

### Ship a new E2B fork commit
1. In the fork checkout at the commit: `setup/build.sh <fork>`; it prints the tag.
2. Set `e2b_sha` in `terraform.tfvars`, apply `-target=module.cell_us_east_1.aws_ecs_task_definition.setup`, run `setup/run.sh` (migrations, idempotent).
3. Apply. api and client-proxy roll with a circuit breaker.
4. Nodes: blue/green through `node_count` ("Adding nodes", step 5). Each termination pauses its boxes first. Never restart orchestrators in place on a node with boxes you cannot afford to pause.

### Adding nodes
Run the commands in "Adding nodes" and "Offboarding a person" from the repository root.

`node_count` in `prod/terraform.tfvars` is the one setting. It is the ASG desired capacity (1..10; `max_size` is 10), the `nodes-below-min` alarm threshold (fewer than `node_count` nodes in service), and sets the edge cap `MAX_RUNNING_UNITS = 2 * (12 * node_count - 2)`. The ASG `min_size` is `min(2, node_count)`, at most `node_count` and below it from 3 nodes up, so scale-in from 2N to N never meets the minimum.

The cap counts capacity units of running sandboxes, by memory: a person or project box is 4096 MB (`edge/template.mjs`, default `memoryMB`) and costs 2 units; a child sandbox is 2048 MB (the `mumbo-child` template build argument) and costs 1 (`edge/capacity.mjs`). Twelve boxes per node is 48 GiB of guest hugepages (`hugepages` in `prod/modules/cell/nodes.tf`) divided by 4 GiB; 2 boxes of headroom are subtracted in total. Boxes and children share the cap, and a child create is refused at the limit like a box create. The cap is approximate: the edge counts, then creates, so concurrent creates can pass the limit together, and the headroom absorbs that. Project boxes use the person template until `PROJECT_TEMPLATE` is set. `box_ram = 8192` in `prod/modules/cell/control.tf` is only the E2B tier's per-sandbox RAM ceiling, not a box size. Limits: 2 nodes 44 units (22 boxes), 3 nodes 68, 4 nodes 92.

The edge also gets `MAX_RUNNING_BOXES = 12 * node_count - 2`, read only by edge images from before the units change, so a rollback to one stays capped. Remove it from `prod/modules/edge/edge.tf` (and its guard in `edge/config.test.mjs`) when no such image can be rolled back to.
1. Edit `node_count`. Run `terraform -chdir=deploy/boxes/prod plan`. Expect `module.cell_us_east_1.aws_autoscaling_group.nodes`, `aws_cloudwatch_metric_alarm.ops["nodes-below-min"]` (threshold), `module.edge_us_east_1.aws_ecs_task_definition.edge` (replaced) and `module.edge_us_east_1.aws_ecs_service.edge`. Read every other line: `APPROVER_EMAILS` and the `NTFY_TOPIC` secret must not change.
2. Apply. New nodes boot from the current launch template, join `orchestrators.boxes.internal` and take new boxes; existing boxes stay where they are.
3. Verify. The ASG must show `node_count` twice:
   ```sh
   aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names mumbo-boxes-nodes \
     --query 'AutoScalingGroups[0].[DesiredCapacity,length(Instances[?LifecycleState==`InService`])]'
   ```
   The edge rollout must end on the new task definition revision: run `edge_rollout` ("Ship a new edge", step 4) and continue only when it returns 0. Then read the cap the revision carries:
   ```sh
   aws ecs describe-task-definition --task-definition mumbo-boxes-edge \
     --query "taskDefinition.containerDefinitions[?name=='edge'].environment[] | [?starts_with(name, 'MAX_RUNNING')]"
   ```
   The `nodes-below-min` alarm reads `GroupInServiceInstances` (group metrics are enabled on the ASG) and returns to OK once the new nodes are in service.
4. Lowering `node_count`: only when the running units fit under the new limit. Count them with the E2B tunnel of "Offboarding a person" step 4 (`E2B_API_URL`, `E2B_API_KEY`):
   ```sh
   (cd deploy/boxes/edge && node -e "import('./capacity.mjs').then(async c=>{const {Sandbox}=await import('e2b');console.log(await c.runningUnits({Sandbox}))})")
   ```
   The result must be at most `2 * (12 * new_count - 2)`. Surplus nodes terminate through the drain hook: their boxes pause and resume on the remaining nodes. The same check applies when blue/green goes back from 2N to N.
5. Blue/green node upgrades go through `node_count` only; never apply while the ASG desired capacity differs from `node_count`, and never change it with `set-desired-capacity` or a decrementing terminate. The ASG prefers the oldest launch template at scale-in, but it rebalances Availability Zones first, so protect the new nodes and check the result.
   1. Set `e2b_sha` and `node_count = 2N` (N at most 5) and apply. The unit cap doubles while both sets run. Wait until the ASG shows 2N in service and the new nodes are in `orchestrators.boxes.internal`.
   2. List the new nodes (those on the group's latest launch template version) and protect them from scale-in:
      ```sh
      LT=$(aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names mumbo-boxes-nodes --query 'AutoScalingGroups[0].LaunchTemplate.Version' --output text)
      NEW=$(aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names mumbo-boxes-nodes \
        --query 'AutoScalingGroups[0].Instances[].[InstanceId,LaunchTemplate.Version,LifecycleState]' --output text \
        | awk -v v="$LT" '$2==v && $3=="InService" {print $1}')
      echo $NEW    # must list N instances
      aws autoscaling set-instance-protection --auto-scaling-group-name mumbo-boxes-nodes --protected-from-scale-in --instance-ids $NEW
      ```
   3. Run the unit check of step 4 for N. If it fails, pause or kill specific boxes (for example, `offboard.mjs` for departed people, or children with `sandbox_kill`) until the count fits, then continue.
   4. Set `node_count = N` and apply. The old nodes terminate, each pausing its boxes through the drain hook.
   5. Remove the protection and verify that every in-service node runs the group's latest launch template version:
      ```sh
      aws autoscaling set-instance-protection --auto-scaling-group-name mumbo-boxes-nodes --no-protected-from-scale-in --instance-ids $NEW
      aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names mumbo-boxes-nodes \
        --query 'AutoScalingGroups[0].[LaunchTemplate.Version, Instances[].[InstanceId,LaunchTemplate.Version,LifecycleState]]'
      ```
      Replace a straggler on an older version with `aws autoscaling terminate-instance-in-auto-scaling-group --instance-id <id> --no-should-decrement-desired-capacity`; it drains through the hook and the ASG launches a replacement on the latest version.

### Offboarding a person
Deleting a box and its backup does not remove the person's access. A domain-admitted person (`@mumbo.si`, `@cambrialabs.ai`) would sign in again and get a new empty box, and an existing oauth2-proxy session stays valid for up to 168 hours. Do steps 1 to 3 in order, then 4. Run from the repository root.
1. Disable the account in Google Workspace (Admin console, Directory, Users, the person, Suspend user).
2. Ban the user in Supabase (dashboard of project `qkvcouccrhyjiarkauyo`, Authentication, Users, the person, "..." menu, Ban user). Ban also blocks signing up again with the address; Delete user only removes the record and lets the address sign up anew.
3. Deny the address at the edge. Precondition: the live `edge_tag` (`prod/terraform.tfvars`, applied) must be an edge image that contains `!address` handling in `admitted()`; otherwise the entry silently denies nobody. Ship the edge from this branch first ("Ship a new edge"). The allowlist accepts `!<address>` entries, an exact address (case-insensitive) that is refused before any allow match; the edge checks the allowlist on every request, so it also cuts off a live session. A malformed `!` entry stops the edge at startup. Append it (the bang part is single-quoted because `!` triggers history expansion inside double quotes in interactive bash and zsh):
   ```sh
   P=/mumbo/boxes/allowed-emails
   V=$(aws ssm get-parameter --name $P --query Parameter.Value --output text)
   [ -n "$V" ] && aws ssm put-parameter --name $P --type String --overwrite --value "$V"',!<email>'
   [ "$(aws ssm get-parameter --name $P --query Parameter.Value --output text)" = "$V"',!<email>' ] && echo OK
   ```
   Continue only if `OK` is printed. Then roll the edge and wait:
   ```sh
   aws ecs update-service --cluster mumbo-boxes-e2b --service edge --force-new-deployment
   aws ecs describe-services --cluster mumbo-boxes-e2b --services edge --query 'services[0].deployments[].rolloutState'
   ```
   Wait until only `COMPLETED` is shown. Without this step an existing session stays valid for up to 168 hours. Rotating the oauth2-proxy cookie secret (`/mumbo/boxes/cookie-secret`) with the same forced deployment signs everyone out at once; use it only if all sessions must end.
   Deny entries are exact addresses. Add a `!` entry for each Workspace alias of the person; a plus-address (`name+x@mumbo.si`) is a different address and is stopped only by step 1 (the disabled account). Owned projects stay tied to the address, so removing a deny entry later hands them to whoever holds that address.
4. Delete the data. Run `npm ci --prefix deploy/boxes/edge` once. The script needs the E2B API, the edge's Redis (ElastiCache `mumbo-boxes-edge`, not MemoryDB) to list owned projects, and AWS credentials that may list and delete object versions in the backup bucket. Open both tunnels in the same shell, in the background:
   ```sh
   NODE=$(aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names mumbo-boxes-nodes \
     --query 'AutoScalingGroups[0].Instances[?LifecycleState==`InService`]|[0].InstanceId' --output text)
   aws ssm start-session --target $NODE --document-name AWS-StartPortForwardingSessionToRemoteHost \
     --parameters host=api.boxes.internal,portNumber=3000,localPortNumber=13000 &
   EP=$(terraform -chdir=deploy/boxes/prod output -raw edge_redis_endpoint)
   aws ssm start-session --target $NODE --document-name AWS-StartPortForwardingSessionToRemoteHost \
     --parameters host=$EP,portNumber=6379,localPortNumber=16379 &
   export E2B_API_URL=http://127.0.0.1:13000
   export E2B_API_KEY=$(aws secretsmanager get-secret-value --secret-id mumbo-boxes/e2b --query SecretString --output text | jq -r .TEAM_API_KEY)
   export REDIS_URL=rediss://127.0.0.1:16379 REDIS_SERVERNAME=$EP   # the server certificate is checked against REDIS_SERVERNAME
   export BACKUP_BUCKET=mumbo-boxes-backup-$(aws sts get-caller-identity --query Account --output text) AWS_REGION=us-east-1
   ```
   Do not echo `E2B_API_KEY`. The script refuses a Redis that holds no `boxes` set (the edge's box index); pass `--allow-empty-store` only if the edge has never created a box. Then:
   ```sh
   node deploy/boxes/edge/offboard.mjs <email>                    # dry run: sandbox ids with owners, backup versions, owned projects
   node deploy/boxes/edge/offboard.mjs <email> --delete <email>   # kill, delete, list again, fail if anything remains
   kill %1 %2                                                     # close the tunnels
   ```
   `--delete` kills the person's boxes and children (metadata `user` or `owner` equal to the email, nobody else's) and deletes every backup version under `users/<sha256 of the lowercased email>/`.
5. Projects the person owns are listed, never deleted. Killing one or transferring it is the founder's decision. To kill a project box, with the tunnel and variables of step 4 still set: `(cd deploy/boxes/edge && node -e "import('e2b').then(({Sandbox})=>Sandbox.kill('<sandbox id from the dry run>'))")`; there is no transfer command today.
6. The edge drops its Redis record of a killed box on its next sweep. The person's chats and files live in the box and its backup, which step 4 removes. Not removed: the audit records of approvals (`audit/approvals/` in the backup bucket, kept on purpose), and pause snapshots of a box that was paused. Those are objects named by an E2B build UUID (`<uuid>/memfile`, `rootfs.ext4`) in the templates bucket (`mumbo-boxes-templates-<account id>`), not by the person; the bucket's lifecycle rule expires only noncurrent versions (14 days), so a current snapshot object does not expire. Whether E2B deletes those objects when a sandbox is killed is not verified; treat them as retained until the boxes session confirms or adds a cleanup.

### Ship a new edge
Precondition for the first edge from B35 on: its `project_message` posts to Superagent's relay route on the project box (`packages/mumbo/superagent/UPSTREAM.md` S9) with no fallback, and a project box without that route answers `relay_unavailable`, a project box created meanwhile included. So first merge S9 to `main`, rebuild the `mumbo-web-prod` image, rebuild the `mumbo-box` template from it ("Rebuild the box template") and move every project box to that build ("Moving a box to a new template build"); only then ship the edge.

Run from the repository root. The image is built from `git archive` of the commit, so it holds exactly that commit's `deploy/boxes/edge` (no uncommitted edit or untracked file) and matches its tag; `.dockerignore` keeps tests, `offboard.mjs`, `restore-version.mjs`, `node_modules` and `.env` out. The build runs `node edge.mjs --check` (`imageCheck` in `edge/edge.mjs`), which fails when a module, a dynamically imported module or a file `main()` reads (`runtimeFiles()`) is missing from the image.
1. Build and push (ECR tags are immutable, so a pushed tag always names that commit's image):
   ```sh
   C=$(git rev-parse --short=10 <commit>)
   REG=$(aws sts get-caller-identity --query Account --output text).dkr.ecr.us-east-1.amazonaws.com
   B=$(mktemp -d) && git archive "$C" deploy/boxes/edge | tar -x -C "$B"
   aws ecr get-login-password --region us-east-1 | docker login -u AWS --password-stdin "$REG"
   docker build --platform linux/amd64 -t "$REG/mumbo-boxes/edge:$C" "$B/deploy/boxes/edge" && docker push "$REG/mumbo-boxes/edge:$C"
   rm -rf "$B"
   ```
2. Set `edge_tag = "<C>"` in `deploy/boxes/prod/terraform.tfvars` and run `terraform -chdir=deploy/boxes/prod plan`. Expect `module.edge_us_east_1.aws_ecs_task_definition.edge` (replaced) and `module.edge_us_east_1.aws_ecs_service.edge` (updated); read every other line. 3. Apply. The apply returns once ECS has the new task definition, before any task of it runs.
4. Wait for the rollout. Define `edge_rollout` once per shell (bash or zsh):
   ```sh
   edge_rollout() {
     td=$(aws ecs describe-task-definition --task-definition mumbo-boxes-edge --query taskDefinition.taskDefinitionArn --output text) \
       || { echo "edge_rollout: describe-task-definition failed"; return 2; }
     echo "edge_rollout: waiting for $td"
     for i in $(seq 120); do
       sleep 15
       d=$(aws ecs describe-services --cluster mumbo-boxes-e2b --services edge \
         --query 'services[0].deployments[].[status,taskDefinition,rolloutState,runningCount]' --output text) \
         || { echo "edge_rollout: describe-services failed"; return 2; }
       echo "$d"
       echo "$d" | awk -v td="$td" '$3 == "FAILED" || ($1 == "PRIMARY" && $3 == "COMPLETED" && $2 != td) {bad = 1} END {exit !bad}' \
         && { echo "edge_rollout: ROLLED BACK, the edge is not on $td"; return 1; }
       echo "$d" | awk -v td="$td" '{n++} $1 == "PRIMARY" && $2 == td && $3 == "COMPLETED" {ok++} END {exit !(n == 1 && ok == 1)}' \
         && { echo "edge_rollout: done on $td"; return 0; }
     done
     echo "edge_rollout: TIMED OUT after 30 minutes, the edge is not on $td"; return 2
   }
   edge_rollout
   ```
   `td` is the newest active revision of family `mumbo-boxes-edge`, the one the apply registered. Each line printed is a deployment: status, task definition, rollout state, running tasks. It polls every 15 seconds, at most 120 times, and returns:
   - 0: exactly one deployment is left, `PRIMARY` and `COMPLETED` on `td`. The rollout is done.
   - 1: a rollback. A deployment is `FAILED`, or the `PRIMARY` deployment is `COMPLETED` on an older revision. Go to step 6.
   - 2: no verdict. Either 30 minutes passed with the rollout still in progress, or an `aws` call failed. Read the events of step 6, then run `edge_rollout` again.
5. Only after it returns 0, commit `terraform.tfvars` (`deploy(boxes): ship edge <C>`).
6. Rollback (`edge_rollout` returned 1, or the `edge-deploy-failed` notification): the circuit breaker put the previous revision back. Read why; a task that crashes at start logs its error as its last lines:
   ```sh
   aws ecs describe-services --cluster mumbo-boxes-e2b --services edge --query 'services[0].events[:5].[createdAt,message]' --output text
   aws logs tail /mumbo-boxes/edge --since 30m | tail -50
   ```
   Then set `edge_tag` back to the tag of the revision that runs, so a later apply does not deploy the failed image again, apply, and run `edge_rollout`:
   ```sh
   aws ecs describe-task-definition --task-definition "$(aws ecs describe-services --cluster mumbo-boxes-e2b --services edge --query 'services[0].taskDefinition' --output text)" \
     --query "taskDefinition.containerDefinitions[?name=='edge'].image" --output text
   ```
   Fix the cause in a new commit and ship that from step 1.

Pending after the edge revision that reads `SUPABASE_ANON_KEY` as a plain value is steady (deployment completed, no rollback): delete the `prod/supabase-anon-key` entry from `module.edge_us_east_1.aws_iam_role_policy.exec_edge` in `prod/modules/edge/edge.tf` and apply. Until then the exec role keeps that grant, so a circuit-breaker rollback to an older edge task definition, which reads the key from SSM, can still start.

For `xsession`, the desktop's launchers bring the running Chrome to the front (`wmctrl -x -a google-chrome`) and never start a second Chrome; for any other user `google-chrome` is plain Chrome on its own profile. The desktop terminal stays, as `xsession`. B20's Browser tab raises and maximizes Chrome with `wmctrl` and never starts it: it relies on `mumbo-browser` to keep Chrome running.
- **Display and live view (KasmVNC).** KasmVNC 1.5.2 (`KASMVNC` and `kasmvncStep` in `edge/template.mjs`) is one process, `Xkasmvnc`: the X server for `:1`, which encodes only the rectangles that changed, and the live view, its web client and WebSocket on the box address and the live view's port, which only the edge reaches: 881 on the B24 template, below the box's unprivileged port floor, which `Xkasmvnc` binds through its file capability `cap_net_bind_service` (`KASMVNC_BIND_STEP`; only root and the group `xvnc` may run it, mode 0750), and 6080 before it. It has no raw VNC port. It runs as the system user `xvnc` (no home, no login), which `browser` can neither signal nor impersonate: whatever answers on the live view's port serves pages on dsh's origin, and `browser` runs Chrome. `start.sh` starts it again unless `xvnc` runs one (`pgrep -u xvnc -x Xkasmvnc`). The template downloads `https://github.com/kasmtech/KasmVNC/releases/download/v1.5.2/kasmvncserver_debian_bookworm_1.5.2_amd64.deb` and installs it only when its sha256 is `5f4bfda43e89178782eac37ae463b1d95d16ac5e45da8b7989ec75404e764993`; otherwise the build fails. Its log is `/tmp/xvnc.log`. `start.sh` starts it with these flags:
  - `-auth /run/x11/auth`: only holders of the X cookie reach `:1`. On the B24 template the cookie is `root:desktop`, mode 0640: root and the group `desktop` (`browser`, `xvnc`, `xsession`, and `desktop`, the user computer use and the Browser tab's `wmctrl` run as). Before it, `browser` owns it, and `start.sh` gives it group `xvnc` and mode 0640 so the server can read it.
  - `-geometry 1600x900 -depth 24`: the size before a viewer resizes it, and the 24-bit depth Chrome needs.
  - `-nolisten tcp`: X itself listens on its local sockets only.
  - `-interface $ip -websocketPort $LIVE_PORT`: the box address and the live view's port, from the template's marker (`PORTS` in `edge/edge.mjs`; 6080, the port websockify used, without one). The edge maps `/desktop/<path>` to `/<path>` there; KasmVNC serves its client at `/` and accepts the WebSocket on any path.
  - `-httpd /usr/share/kasmvnc/www`: its web client.
  - `-DisableBasicAuth -sslOnly=0 -SecurityTypes None`: KasmVNC's login, TLS and VNC password are off. The edge terminates TLS, signs the person in, and refuses a WebSocket, or any request but a read, whose Origin is not the box's own host: it is the only gate. Without a login, KasmVNC's owner API (`/api/`) answers 401.
  - `-PublicIP 127.0.0.1`: without it, KasmVNC asks public STUN servers for the box's address at start and exits when none answers.
  - `-FrameRate 30`: at most 30 updates a second to each viewer.
  - `-RectThreads 2`: two encoder threads. KasmVNC 1.5.2 accepts the flag but does not apply it: its encoder pool has one thread per CPU core the CPU reports, which is at most 2 on a 2 vCPU box. Recheck this before giving boxes more vCPUs.
  - `-IgnoreClientSettingsKasm`: a viewer cannot change the frame rate, quality or video settings, which KasmVNC otherwise lets its client set for the whole server.
  - `-DLP_ClipTypes text/plain`: the clipboard carries text only, no HTML or images, in both directions.
  - `-DLP_ClipSendMax 262144 -DLP_ClipAcceptMax 262144`: at most 256 KiB per copy, from the box to the viewer and from the viewer to the box; a larger copy is dropped and logged.
  - `-DLP_ClipDelay 500`: at least 500 ms between clipboard sends to a viewer. KasmVNC has no rate limit for copies from the viewer to the box.
  - **Screen size.** The screen follows the viewer's size (`resize=remote` in the edge's `/desktop/` redirect), so a phone gets a phone-sized desktop, capped at 1600×900. KasmVNC has no server-side limit, so the template adds `<style>#noVNC_container>div{max-width:1600px;max-height:900px}#noVNC_displays_button{display:none!important}</style>` to its web client's `index.html` and `vnc.html`. That element's size is what the client asks for; the hidden Displays button would open additional displays (`screen.html`), which size the screen to their own windows. The build fails when either page lacks the style. A larger window shows the 1600×900 desktop and an empty margin. Only the client enforces the cap: a viewer that asks for a larger screen, such as `screen.html` opened by hand or a raw client, gets it, up to 32768×32768.
  - **Not used.** KasmVNC's WebRTC transport always binds UDP on the live view's port on every address; its client leaves it off, the ALB cannot carry it, and `start.sh` drops it except on loopback. Its H.264 mode needs FFmpeg, which the template does not install, so it encodes JPEG and WebP. Chrome gets no `--enable-unsafe-swiftshader` (no WebGL fallback).
  - **The `/desktop/` entry.** The edge redirects `/desktop/` to `/desktop/vnc.html?autoconnect=1&resize=remote&path=desktop/websockify&show_control_bar=1`. KasmVNC's client and noVNC both read these from the query. `show_control_bar=1` keeps KasmVNC's control bar, clipboard and remote resize on inside the Desktop tab's frame, where its defaults turn them off. `@mumbo/box-links` uses `https://<public host>/desktop/` unchanged. Every response from port 6080 carries a second Content-Security-Policy, `connect-src 'self' wss://<public host> data:` (`data:` for the client's built-in video decoder samples): the client connects to whatever `host`, `port` and `path` its URL names and, in Chrome, sends the local clipboard there on the first click, so a link from any site could otherwise aim it at another server. `-DLP_ClipTypes` binds the box's server only. Every public-host response carries `Cross-Origin-Opener-Policy: same-origin-allow-popups`, so a page that opened dsh keeps no handle to its frames: the client in the Desktop tab's frame accepts clipboard, resize and disconnect messages from any origin.

**How `box_step_disk` was sized.** E2B gives a build `disk_mb` of free space after its own provisioning and before the template's steps (`template.mjs` `runCmd`), and the steps' installs come out of it. They were measured on 2026-11-09 by running them in `node:24-bookworm` (the web image's base, `deploy/Dockerfile`) after the web image's and E2B's provisioning packages, comparing `du -sxm /` before and after: mumbo-box (desktop packages and Chromium) 1007 MiB, mumbo-project (git, gh) 41 MiB, mumbo-child no steps. After any build the steps' real use is `disk_mb` − 256 − the free MiB of the smoke line; raise `box_step_disk` when that plus 256 nears 2048, or when `template.mjs` gains steps.

A box keeps its rootfs, so it keeps the disk and the software of the build it was created from. List boxes and their disk sizes (with the variables of "Rebuild the box template"; one page holds 100):
```sh
curl -s -H "X-API-Key: $E2B_API_KEY" "$E2B_API_URL/v2/sandboxes?state=running,paused&limit=100" \
  | jq -r '.[] | [.sandboxID, .alias, .diskSizeMB, (.metadata.user // ("child of " + .metadata.owner)), .startedAt] | @tsv'
```
A box (metadata `user`: an email, or `project:<id>` for a project box) whose `diskSizeMB` is below its template's in the templates listing is on an older build. Children (metadata `owner`) are short-lived; leave them. The edge recreates a missing box from its backup at the next visit, so moving a box is: back it up, kill it, let the next visit restore it.
1. Ask the person (for a project box, its members) to stop working in it: no agent turn running, nothing unsaved. Then wait for the box's next backup; the sweep backs up every `BACKUP_MINUTES` (10, the default, in production). The newest line must be later than the moment they stopped:
   ```sh
   aws logs filter-log-events --log-group-name /mumbo-boxes/edge --start-time $(( ($(date +%s) - 1800) * 1000 )) \
     --filter-pattern '{ $.msg = "backup" && $.box = "<sandbox id>" }' --query 'events[].message' --output text
   ```
2. Kill it, with the E2B tunnel and variables of "Offboarding a person" step 4: `(cd deploy/boxes/edge && node -e "import('e2b').then(({Sandbox})=>Sandbox.kill('<sandbox id>'))")`.
3. The next visit (a project box: a member opening the project) creates a box from the current template and restores the backup into it; the edge drops its record of the old box on its next sweep. In the listing, the new box has the template's `diskSizeMB`.

A move keeps what the backup holds (`backupCommand` in `edge/edge.mjs`): `/root/.dsh` (Sessions, settings, schedules; SQLite as consistent copies) without dsh's temporary directory, `/root/projects` and, on a project box, the Superagent's `/root/work`, without `node_modules` (SQLite as consistent copies), the uploads of agent containment in `/var/lib/mumbo/attachments` without their cache, and `/home/browser`, `/home/shared` and, on the B24 template, the desktop session's `/home/xsession` (the Chrome profile, desktop settings, Downloads within the limits of "Person box desktop and Google Chrome") without caches. It loses everything else: work after the last backup, running processes (terminals, dev servers, an agent turn in progress), `node_modules` (reinstall), whatever was installed or written outside those paths (`apt`, `pip` or global `npm` installs, `/root` dotfiles such as `.gitconfig` or `.ssh`, the agent's scratch home `/home/agent`, `/tmp`), and browser caches. The sandbox id changes.

### Agent containment (B24)
A box on the B24 template runs the model's commands as the user `agent` instead of root and keeps its file tools in the model roots (the harness's Agent Note `.agents/notes/implemented/architecture/2026-11-10-agent-containment-run-as-and-model-roots.md`). Two gates in `start.sh` (`startScript` in `edge/edge.mjs`) decide what a box gets: the template's marker `/usr/local/share/mumbo/ports` (`PORTS_STEP` in `edge/template.mjs`), and an image whose `packages/subprocess/subprocess-local` names `serverIdentity`. A template without the marker and an image without the harness keep the behaviour of the edge before B24. An image with the harness on a template without the marker stops `start.sh` with `mumbo-box: this image runs agent containment (B24), which needs a template built with it`, and the edge reports the create as failed.
- **Template (marker).** The template installs `nftables`, `acl` and (person boxes) `libcap2-bin`, gives `Xkasmvnc` `cap_net_bind_service` and lets only root and the group `xvnc` run it (`root:xvnc`, mode 0750), and creates the users `agent` and `mcpserver`, on person boxes also `browsermcp`, `desktop` and `xsession`, on project boxes the GitHub proxy's system user `ghproxy`, and the groups `workspace` (agent, xsession) and `workspace-read`; `shared` gains agent and xsession, `desktop` gains browser, xvnc and xsession, and person boxes get the system group `uploads` (browser, browsermcp; `browsermcp` is in no other group) (`usersSteps`). A template built before `uploads` stops `start.sh` with `mumbo-box: the template has no group uploads`: rebuild it. Their ids are whatever is free when the template is built, because E2B's own account `user` can take any of them: `start.sh` reads them at each start and writes them into the containment rows. At each start, before any user's process runs, `start.sh` sets `net.ipv4.ip_unprivileged_port_start=1024` (Docker's floor, and maybe a VM image's, is 0), `fs.protected_hardlinks=1` and `fs.protected_symlinks=1`, remounts `/proc` with `hidepid=2`, and takes the set-user-ID bit off `su` and `sudo`, checking each. It then writes the firewall, one native nftables table `inet mumbo` for IPv4 and IPv6, to `/root/.mumbo/firewall.nft` (root's, 0600), loads it with `nft -f`, which replaces the whole table in one transaction, and checks that it is loaded; `nft list table inet mumbo` shows it. It is native nftables because E2B's kernel has nf_tables but not `xt_owner`, so iptables' `-m owner` fails there ("Extension owner revision 0 not supported"); the table matches the socket's user with `meta skuid`. Its output chain refuses every process in the box, root's included, a TCP connection, on any address, to E2B's envd (49983, which runs commands as root: root's dsh fetches pages for the model, and the edge's commands reach envd from outside the box), every user but root one to dsh's port, the live view's port, the Mumbo door (882) and 5900 to 5999, and every user but root and `browsermcp` one to the browser's debugging port (9222). It accepts the allowed users first and resets every other connection to those ports, so a socket whose user nftables cannot read (one with no file) is refused, as under iptables' `xt_owner`. The project box's GitHub proxy, which tunnels any CONNECT that is not GitHub's, runs as `ghproxy` once its certificates are ready, so these rules cover its tunnels too. Nothing that runs as an unprivileged user needs another user's `/proc`: dsh, which watches its children's process table, runs as root. Its input chain drops 9222 and 5900 to 5999 from beyond loopback and UDP on the live view's port (a template before the marker gets best-effort iptables INPUT rules for these on person boxes instead). Every one of these steps is fatal: a box whose kernel refuses one does not start dsh, and the edge reports the create as failed. The template's last step, the nftables smoke check (`NFT_SMOKE_STEP`), loads a probe table `inet mumbo_probe` that accepts root's connections to port 47999 and resets every other one, listens on 127.0.0.1:47999 as root, and fails the build unless root connects and `agent` is refused; it deletes the table and stops the listener either way, so a template whose start script cannot load its firewall is never published.

### Model routes
Boxes reach models only through the edge model host (`llm.` host, port 8081), with their box token as the API key; every route checks the token, the source address (`BOX_EGRESS_IPS`), the founder's stop switch, the daily request budget (`DAILY_MODEL_REQUESTS`) and the daily token budget (`DAILY_TOKENS_USER`, `DAILY_TOKENS_PROJECT`; usage read from each response), and swaps the token for the edge's own key.

| Route | Box side | Upstream | Body cap |
|---|---|---|---|
| DeepSeek | `DEEPSEEK_BASE_URL=https://<llm host>/anthropic`, search `/v1/tools/…`, `/models` | `MODEL_UPSTREAM` (api.deepseek.com), key `mumbo/prod/deepseek-api-key` | none at the edge |
| OpenRouter | dsh-llm-pi-ai route `openrouter`, `baseURL https://<llm host>/openrouter/v1`, written by `startScript` (`/root/.mumbo/models.overlay.yml`) | `https://openrouter.ai/api/v1/chat/completions` and `/models` only, key `mumbo-boxes/openrouter` (`OPENROUTER_API_KEY`) | 20 MiB (413 and the connection closed; a larger `content-length` is refused before reading); dsh keeps images to 12 MiB |

OpenRouter rules, all in `openrouterBody` (`edge.mjs`); a refused request gets 400 and nothing is forwarded:

- **Models:** only the exact ids in `OPENROUTER_MODELS` (tfvar `openrouter_models`, default `qwen/qwen3.8-27b,qwen/qwen3.5-9b`); `/openrouter/v1/models` lists only those ids.
- **Messages:** each message needs a role (`system`, `developer`, `user`, `assistant`, `tool`) and keeps only the fields pi-ai writes: `role`, `content`, `name`, `tool_calls`, `tool_call_id`, `reasoning`, `reasoning_content`, `reasoning_text`, `reasoning_details`. `content` is a string, null, absent or an array of parts; each part is rebuilt from its known keys: `{type: "text", text, cache_control?}` with a string `text` (`cache_control` becomes `{type: "ephemeral"}`), or `{type: "image_url", image_url: {url, detail?}}` with a `data:image/` URL. Any other shape, `file` (OpenRouter's paid PDF parser), `input_audio`, `video_url` and remote image URLs are refused, so the body cap bounds every image and OpenRouter fetches nothing.
- **Tools:** every `tools[]` entry has `type: "function"`; `tool_choice` is a string or `{type: "function", …}`.
- **Fields:** only `OPENROUTER_FIELDS` pass: `model`, `messages`, `stream`, `stream_options`, `max_tokens`, `max_completion_tokens`, `temperature`, `top_p`, `stop`, `seed`, `tools`, `tool_choice`, `parallel_tool_calls`, `response_format`, `reasoning` (what dsh's pi-ai sends, plus standard sampling fields). Everything else, such as `provider`, `models`, `plugins`, `route`, `transforms`, `preset`, `web_search_options`, `usage` or `include_reasoning`, is dropped.
- **Set by the edge:** `stream: true` and `stream_options: {"include_usage": true}` (dsh always streams; the final chunk carries usage), `reasoning.exclude: false` when `reasoning` is present (reasoning is reported, not hidden), and `provider: {"data_collection":"deny","zdr":true}` (no endpoint that trains on prompts; zero-data-retention endpoints only).
- **Headers:** upstream gets only `content-type`, the OpenRouter key and pi-ai's `x-session-id` (at most 128 of `A-Za-z0-9._:-`, never a box token; it keeps a Session on one provider for prompt caching).
- **Usage:** `prompt_tokens + completion_tokens` (reasoning tokens are inside `completion_tokens`). A box that drops a stream before its usage chunk is charged ceil(request bytes without image data / 3), plus per image its pixels / 784 (Qwen-VL's one token per 28 x 28 patch; width and height from the PNG, GIF, WebP or JPEG header) at most `OPENROUTER_IMAGE_TOKENS` (default 16384, Qwen-VL's per-image maximum, also charged when the header cannot be read; set it in the edge task's `environment` in `prod/modules/edge/edge.tf`), plus ceil(streamed characters / 3). An upstream error is not charged. Each forwarded call (`/models` included) and each OpenRouter request refused with 400 or 413 logs one `"edge":"model"` line with its status.

- **Add or remove a model:** change `openrouter_models` and apply. The edge enforces it at once; a box lists the new set when it is next created (`startScript`), with metadata from dsh's pi-ai catalog unless `OPENROUTER_BOX_MODELS` in `edge.mjs` overrides it; override a context window only to the `context_length` that `/openrouter/v1/models` reports. A box created earlier keeps listing a removed model, whose requests get 400.
- **Disable:** set `openrouter_models = ""` and apply: the paths answer 404, neither the task nor Terraform reads the key, and new boxes get no OpenRouter route.
- **No ZDR endpoint:** if requests fail with OpenRouter's 404 about data policy, set `openrouter_zdr = false` and apply; `data_collection: deny` stays.
- **Sessions:** a Session keeps the model it started with; to use images, the user starts a Session on a Qwen model.

### GitHub: the agent is the mumbo-bot App
The coding agent writes to GitHub as `mumbo-bot[bot]`, the bot user (id 341797844) of the `mumbo-bot` App (5295930, owned by and installed on `callgideon` as installation 170921050; credentials in Secrets Manager `mumbo-boxes/github-app`). - `a new pull request may set only title, body, head, base, draft, maintainer_can_modify` (403): `POST /pulls` named another key, such as `issue`, which would turn a person's issue into the agent's pull request.

### Merge approvals

A person's door key (`edge/keys.mjs`, spec section 10) lets their own AI tools, such as Claude Code, reach mumbo over MCP as them, at the door endpoint (next section).
- **Minting:** only the signed-in person, on the key manager at `https://<approve host>/keys`, an origin no box serves: a page on the public host, which the person's own box serves, could otherwise open the manager in a popup and read a new key. `https://<public host>/home` only links to it, and `/keys` and `/keys/revoke` on the public host redirect (302) to it. A key has a name, scopes (`read`, `prompt`, `workspace`), the projects it may reach (only projects the person is a member of), and a lifetime of 7, 30, 90 (preselected) or 365 days, or none. The key is shown once, in the answer to the create (`cache-control: no-store`), and is never logged. The same page lists the person's keys (scopes, projects, created, expires, last used, revoked) and revokes them. Its POSTs need `Origin: https://<approve host>`, a form navigation (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`) and the day's CSRF token (HMAC of the edge key, `keys-csrf`). Every key page has `Cross-Origin-Opener-Policy: same-origin` and `frame-ancestors 'none'`. The public host answers 403 to every service-worker script fetch (a `Service-Worker` request header), so no worker a box serves sits in front of `/home`.
- **Format:** `mumbo_pat_`, 32 base62 characters, then the CRC32 of everything before it as 6 base62 characters (jumbo's `key_format.py`); 48 characters. A malformed key or a bad checksum is refused without a store read.
- **Storage:** the edge's Redis (ElastiCache `mumbo-boxes-edge`) holds only the SHA-256: `doc:key:<sha256 hex>` = JSON `{ id, owner, name, scopes, projects, createdAt, expiresAt?, revokedAt? }` (epoch ms), `set:keys:<email>` = the hashes of that person's keys, and `doc:key-used:<key id>` = `{ at }`, the last verified use, written at most once a minute per key by each edge replica (as jumbo does), so it can lag a use by up to a minute. Nothing caches a key, so a revocation holds from the next call.
- **Refusals** (jumbo's codes): `invalid_api_key` 401, `key_revoked` 401, `key_expired` 401 (from `expiresAt` on), `user_disabled` 403 (the owner is off `ALLOWED_EMAILS`, so an offboarding deny entry cuts off every key of the person), `insufficient_scope` 403, `user_key_required` 403 (a box token, the assistant's or a coordinator's), and `project_not_allowed` 403 (a project the key does not list, or one its owner has left).
- **Revoke a person's key as an operator:** open the Redis tunnel of "Offboarding a person" step 4 (`REDIS_URL`, `REDIS_SERVERNAME`), then list their keys and revoke one by its id:
  ```sh
  cd deploy/boxes/edge && node --input-type=module -e "
  import { createClient } from 'redis'; import { redisStore } from './store.mjs'; import { doorKeys } from './keys.mjs'
  const c = createClient({ url: process.env.REDIS_URL, socket: { servername: process.env.REDIS_SERVERNAME } }); await c.connect()
  const keys = doorKeys({ store: redisStore(c) }), [email, id] = process.argv.slice(1)
  if (id) await keys.revoke(email, id); console.log(await keys.list(email)); await c.quit()" <email> [<key id>]
  ```
  Without a key id it only lists. The edge reads the record on every call, so no edge restart is needed.

### The door endpoint
`https://<public host>/mcp` (`https://app.mumbo.si/mcp`) is MCP over Streamable HTTP (`edge/door.mjs`), served on the edge's model listener (:8081). The model listener hands every request whose Host is the public host to the door, before its source address and box token checks, and no model route answers there; the boxes' own endpoint, `https://<llm host>/mcp`, is unchanged and answers a door key 401 `invalid box token`.
- **R-door must be live:** the ALB rule sending host `app.mumbo.si` with path `/mcp*` to the model target group, ranked above the `user` rule (priority 10), past oauth2-proxy. Without it the request reaches oauth2-proxy, which answers with its sign-in, and Claude Code reports the server as failed. The ALB idle timeout must be at least 60 s (it is 3600 s) for 40 s long polls.
- **Point Claude Code at it** with a key minted on the key manager (previous section); replace an older `mumbo` entry with `claude mcp remove mumbo` first:
  ```sh
  claude mcp add --transport http mumbo https://app.mumbo.si/mcp --header "Authorization: Bearer <key>"
  ```
  `/mcp` in Claude Code then lists `whoami`, `project_list`, the Mumbo tools and the project tools (below); `whoami` names the key, its scopes and projects, its owner and its expiry.
- **Authentication:** exactly one `Authorization: Bearer mumbo_pat_…` header, verified on every request (`doorKeys.verify`), so a revocation holds from the next call. Cookies are never read: a browser carrying the sign-in cookie but no key gets 401. A request with any `Origin` header gets 403 `origin_refused`, and the door sends no CORS header: browsers send `Origin` on every POST and cross-origin request, while MCP clients such as Claude Code (Node's fetch) send none.
- **Refusals:** HTTP status plus a JSON-RPC error whose message starts with the code and whose `data.code` is the code; never the key. 401 `invalid_api_key`, `key_revoked`, `key_expired`, each with `WWW-Authenticate: Bearer realm="mumbo"` (Claude Code does not fall back to OAuth while an `Authorization` header is configured, and shows the body); 403 `user_key_required` (a box token), `user_disabled`, `insufficient_scope`, `project_not_allowed`, `tool_undeclared`, `origin_refused`; 429 `rate_limited` (with `Retry-After` in seconds) and `budget_exhausted`; 400 `parse_error` and `invalid_request` (one JSON-RPC message per request, no batches); 405 `method_not_allowed` with `Allow: POST` (any method but POST, answered before its body is read; MCP clients treat a 405 to their optional GET stream and session DELETE as normal); 413 `body_too_large` (over 1 MiB); 404 `not_found` (any other path on the public host).
- **Rate limit:** each key has a bucket of `DOOR_BURST` calls (default 20) refilled at `DOOR_RATE_PER_MINUTE` (default 60) a minute; every request after the key check takes one. The bucket is per edge process: with the edge's 2 tasks a key can get up to twice that, which is enough to stop a runaway client and needs no store round trip. Set either in the edge task's `environment` in `prod/modules/edge/edge.tf`; a value below 1 or not a number stops the edge at start.
- **Dispatcher:** before any tool runs, a `tools/call` must name a tool that declares its scope, whether it takes a project id (in its `project` argument) and whether it causes model turns, or it is refused with `tool_undeclared`; then the key needs the scope and, for a project tool, must list the project while its owner is still a member. A tool that causes model turns takes one request from the owner's `DAILY_MODEL_REQUESTS` budget and needs their `DAILY_TOKENS_USER` budget open, or gets 429 `budget_exhausted`; the turns' own model calls are metered on the model host as usual. Of the door's tools `agent_send`, `project_message` and `task_start` cause model turns. `project_list` lists the projects the key names that its owner is still a member of.
- **Mumbo (B33):** `agent_send`, `agent_read` and `task_reply` (prompt), and `needs_you`, `task_status` and `task_result` (read), are `@mumbo/mcp`'s `door` profile in the owner's person box, whose results the door returns unchanged (`mumboForwarder`). Each call ensures the box, resuming or creating it as a page visit does, then POSTs one `tools/call` to `/mcp` on box port 882 (below 1024, so only root can bind it and no box process can catch the box key during a dsh restart) through the client proxy with the box's own key, `HMAC-SHA256(edge key, "mumbo-mcp:<box id>")` as unpadded base64url (derived for every call, never stored), `x-mcp-principal` = the owner's handle (their email's local part, lowercased, other characters as `-`) and `x-mumbo-key-name` = the door key's name, so a message shows in Mumbo as `[from <handle> via <key name>]`. The person box's start script writes that key to `/root/.mumbo/mcp.key` (mode 0600), exports `MUMBO_MCP_*` and patches `packages/mumbo/mcp/examples/person.overlay.yml` after the assistant's overlay, only when the image ships that file and links `@mumbo/mcp` into `/src/node_modules` (the overlay names the package bare, so an image whose root `package.json` does not depend on it could not load it); project boxes get none of it. The start script is written when a box is created, so a box created by an older edge gets the door only once it is recreated (back it up, kill it, let the next visit restore it). `task_reply` answers questions only: the box refuses tool approvals and plan reviews with `needs_person`. `runs_halt` and `runs_resume` are not on the door. A call takes at most 50 s, inside CloudFront's and the ALB's 60 s: `agent_read`'s `wait_s` (at most 40) is cut after a slow box start. Failures are the tool error `box_unavailable`, with a `{"edge":"door","level":"warn"}` line naming the cause: the box is not ready within 20 s (its start goes on; call again), cannot start, or its route answers no tool result, such as the client proxy's 502 for an image without the overlay. A result the box marks as an error logs the outcome `box_error`.
- **Projects (B34):** `project_status` (read), `project_message` (prompt), and `task_start` and `task_stop` (workspace) each take a `project` the key lists and its owner is still a member of, and reach that project's box as the owner, a member (`projectRelay`): each call ensures the box, resuming or creating it, and sends the owner's signed `x-mumbo-member` header through the client proxy. `project_message` (`kind` `context` only, so a key without `workspace` cannot ask for work) and `task_start` (always `request`, which Superagent's Eval turns into a Ticket) post to the relay route with the caller's `messageId` and the hops member, `{ node: 'door', id: <key name> }`, edge; their results carry the relay's `trigger` and `thread` ids, and a box refusal keeps its code (`relay_off`, `id_reused`, `invalid_request`, or `relay_unavailable` for an older build). `project_status` and `task_stop` call Superagent's management API (`/orchestrator/api/…` with `x-orchestrator-request: 1`), which admits only the owner and `MUMBO_PANEL_ADMINS` (the project owners): `project_status` reads `overview` and `tickets?state=open&limit=20` and returns the project record, problem kinds (at most 10), the open Tickets waiting on any person (`waitingOnPeople`, not only on the caller) and the newest open Tickets (at most 20 each, titles cut to 200 characters, notes 300, summaries 500) and executor load. Titles, notes and summaries come each in a nonce'd `<untrusted-…>` tag, as `@mumbo/mcp` wraps its text, because workers and strangers' issues can steer them; ids, stages, actions, times and problem kinds pass only as tokens (`[A-Za-z0-9._:-]`, at most 128) and counts only as numbers, as do the relay's result, Trigger and Thread ids; `task_stop` POSTs `tickets/<id>/stop` for one Ticket, and a Ticket the named project's box does not have is `not_found`. A management 403 whose text is Superagent's panel-admin refusal (the caller is not a panel admin) is `owner_only` ("only the project's owners can read its status or stop its Tickets"), and any other answer than 200, 400, 404 or 409, other 403s included (a Host or Origin fence, a missing `x-orchestrator-request`: a misconfigured box or edge), is `box_refused` with the box's text, which the `{"edge":"relay","msg":"api refused"}` warn line also carries as `error`; a box's refusal text is cut to 500 characters, and the edge reads at most 8 MiB of any box answer. A call takes at most 50 s, as for Mumbo: a project box not ready within 20 s is the tool error `box_unavailable` (its start goes on, with a `{"edge":"relay","level":"warn"}` line if it fails; call again, with the same `messageId` for a message), and each box request may stay quiet only for what remains of the 50 s. Stopping every Ticket or the executor is not on the door.
- **Reports to members (B36):** the other way, a project box's Superagent reports a reply on a relay Thread with `report_to_member` `{ member, project, thread, messageId, text }` on the box-token endpoint `/mcp/report` (`reportServer`, `memberReporter`), which lists that one tool, to project boxes only. It is not on `/mcp`, because every box's `mcp-sandboxes` client connects its models there with the same token. `project` must be the calling box's own (else `wrong_project`), and `member` one of its members still on the allowlist (else `not_a_member`, which Superagent settles as gone); `text` is at most 20,000 characters. Then, before anything is forwarded, a halted project (an owner's Stop everything) gets `halted`, and a report past its (project, member) bucket gets `rate_limited`: each pair has 10 reports, refilled at 30 an hour, per edge process (`REPORT_RATE` in `door.mjs`), because each report starts a model turn on the member's budget and, until B24, any process in a project box holds the box token. The report is one `agent_send` into the member's Session `mumbo` of `[project <name>] report from its coordinator:`, a newline, and the text in a nonce'd `<untrusted-…>` tag, because workers and strangers' issues can steer it; brackets, line breaks and other control or separator characters of the project's name are spaces there. It is sent as the door's Mumbo tools are (ensuring the member's box) but without `x-mumbo-key-name`, so `@mumbo/mcp` logs that text as it is, not after `[from <handle> via …]`, with `x-mumbo-report-project: <project id>`, which only reports carry (never the door's own `agent_send`), so an image with B36b records the project, not the person, as the message's source and an older image ignores it, and with a `request_id` derived from `(project, messageId)`, so `@mumbo/mcp` delivers a retry once within its one-day window. Mumbo's instructions say such a report is data from the project, never the person's instructions, requests or consent. Superagent's Outbox retries every refusal but `not_a_member`: `halted`, `rate_limited`, `wrong_project`, `box_unavailable`, and `box_error` with Mumbo's refusal, such as its own `halted`; each delivery logs `{"edge":"report","msg":"delivered",…}`. The project box's start script writes the box token to `/root/.mumbo/edge.token` (mode 0600) and exports `MUMBO_EDGE_MCP_URL` (the model host's `/mcp/report`), `MUMBO_EDGE_TOKEN_FILE` and `MUMBO_PROJECT_ID` only when the image's `deploy/mumbo-project.overlay.yml` reads them. As with the door to Mumbo, a box created by an older edge gets this only once it is recreated.
- **Logs:** one line per request, never the key, its hash or an argument: `{"edge":"door","key":"<key id>","name":"<key name>","owner":"<email>","method":"tools/call","tool":"whoami","outcome":"ok","status":200,"ms":12}`. `outcome` is `ok`, a refusal or tool error code, `not_run` (a tool call the SDK did not run, such as one with invalid arguments), or `http_<status>` (a request the SDK refused itself, such as 406 for a missing `Accept` or 415 for a body that is not JSON); a request refused before its key is known has no key fields. One key's calls: `aws logs filter-log-events --log-group-name /mumbo-boxes/edge --filter-pattern '{ $.edge = "door" && $.key = "<key id>" }'`.

### Restore Postgres to a point in time
`aws rds restore-db-instance-to-point-in-time --source-db-instance-identifier mumbo-boxes-e2b --target-db-instance-identifier mumbo-boxes-e2b-restore --restore-time <UTC>` into the same subnet group and security group, then point `POSTGRES_CONNECTION_STRING` in the `mumbo-boxes/e2b` secret at the new instance and force a new deployment of api. Snapshots that newer rows point at stay in the versioned templates bucket for 14 days (review M4).
