# Agent Note: Agent containment through a run-as identity and model roots

Status: implemented

## Problem

A Mumbo box runs `dsh` as root. Everything the model asks for runs as root too: its shell commands, terminals, code runtimes, language servers, jobs and subagent shells, and the file tools, which run inside the `dsh` process. Anyone who can steer the model, a project member or injected content, can therefore read the box token (`DEEPSEEK_API_KEY`), `MUMBO_MEMBER_KEY`, the launch token in `/root/dsh.log`, `/proc/<pid>/environ` of root processes, and the browser profile that holds synced passwords and cards. The box side gives the agent its own non-root `agent` user, file permissions and network rules; the harness has to start the model's processes as that user and stop its file tools, which stay in the root process, from reaching anything else.

## Decision

Two opt-in deployment settings, both off by default so upstream behavior is unchanged.

### Run-as identity on the subprocess provider

`@deepseek-ai/dsh-subprocess-local` takes `runAs`, and optionally further named `identities` in the same form:

```yaml
- id: subprocess
  name: '@deepseek-ai/dsh-subprocess-local'
  config:
    runAs:
      uid: 1001
      gid: 1001
      groups: []
      inherit: [PATH, LANG, LC_ALL, TERM]
      set: { HOME: /home/agent, TMPDIR: /home/agent/tmp, USER: agent, LOGNAME: agent, SHELL: /bin/bash }
      secretNames: [DEEPSEEK_API_KEY, MUMBO_MEMBER_KEY]
```

Every `spawn` and `spawnTerminal` of the provider then starts the target as that identity. The default identity applies to the provider, not to a spawn request, because every model-reachable process except the experimental and harness-owned ones listed below starts through `ctx.subprocess`, and a provider-wide identity covers a spawn path added later without its author opting in. The provider is the one host-plane row a deployment patches; per-Consumer settings would have to be repeated in every Agent Preset realm and would fail open where one was forgotten.

- **Credentials.** The Linux exec bootstrap of the provider (the runner that already restores a target's cwd and environment before `execve`) receives the identity in its root-owned `0600` launch request, then calls `setgroups(groups)`, `setgid(gid)` and `setuid(uid)`, reads `/proc/self/status`, and enters the target only when the real, effective, saved and filesystem ids and the supplementary groups equal the identity. Any refused step or mismatch is a startup error and `done` rejects with `run-as: could not take ...` or `run-as: credentials after the change do not match ...`; the target never runs. Without a user-systemd scope, run-as launches start the bootstrap directly as a detached process group instead of the target, so ordinary, terminal, scoped and unscoped launches share one drop. Node's own `spawn({ uid, gid })` was not used because `node-pty` changes the uid and gid without clearing supplementary groups, and Node's spawn can only clear them, not set an explicit list.
- **Environment.** A run-as child receives only the `inherit` names of the credential-scrubbed `dsh` environment, then the spawn request's explicit entries (an `undefined` entry removes a name), then the `set` values, which replace both. Nothing else from the root environment reaches it. Explicit entries pass because Consumers set them on purpose (for example `DSH_SESSION_ID`, `GIT_INDEX_FILE`, the control-pipe descriptor); requiring every such name in `inherit` would silently drop facts a Consumer relies on.
- **Secret guard.** Before any launch file is written, the provider refuses, with `SubprocessSecretEnvironmentError`, a final environment that contains any `secretNames` entry, compared without case. The check runs on the exact environment the target receives, including launch additions such as `TERM` and `PWD`. Load-time validation separately rejects an `inherit` or `set` name that is a secret, a credential-shaped `inherit` name (the scrub drops it, so inheriting it would do nothing), `uid`, `gid` or a group of `0`, an empty `secretNames`, invalid names, a non-Linux host, and a host whose exec bootstrap is unavailable.
- **Host facts.** At load the provider also requires `os.tmpdir()` (where the root bootstrap's launch requests and tsx module cache live) to be spelled as its real path, so no later write follows a link another user could repoint, and to be owned by this process and writable by no other user, with every ancestor owned by root or this process and not writable by group or others (a sticky ancestor counts only when this process owns the entry below it), and `fs.protected_hardlinks=1`. After the drop the bootstrap sets `no_new_privs` through libc `prctl` and requires empty permitted, effective, and ambient capabilities and `NoNewPrivs: 1` before it enters the target. The box starts dsh with `TMPDIR=/root/.dsh/tmp`.
- **No inherited output.** A run-as child never receives `dsh`'s standard output or error: an output stream a spawn request asks to inherit is read and discarded. `dsh`'s stderr is the root-only `/root/dsh.log`, whose launch-token line the edge parses; forwarding a child's bytes to `dsh`'s logger would let it forge that line too, so the bytes are dropped rather than logged.
- **Shell activity records.** For an interactive `bash -i` or `zsh -i` terminal with activity observation, the record directory is created in `shellActivityDirectory` (default `os.tmpdir()`), stays root-owned with mode `0711`, the startup file is `0644`, and only the two record files are pre-created and owned by the run-as user, so the shell can write its state but cannot add or replace entries. The run-as shell must reach the directory while `dsh`'s temporary directory stays closed to it, so the box sets `shellActivityDirectory: /run/dsh-shell` (root, `0711`); the provider fails at load unless that directory passes the same ownership check as the temporary directory and the run-as user can search it and every ancestor, and then writes through the real path it checked.
- **Spill files.** `spillDirectory` (default: a private directory under `os.tmpdir()`) receives full-output spill files, created `0640`. Under run-as it must pass the temporary directory's ownership check, and spill files go to the real path that check examined. The box makes it `root:agent` with mode `2750`, so the model's shell can read the spill path a result names and the model's `read` opens it through a read-only root.
- **Lookups.** `resolveExecutable` searches the run-as `PATH`, and `terminalEnvironment().defaultShell` reports the run-as `SHELL` (or nothing), never root's account shell.
- **Named identities.** A helper process that acts for the model but needs access `agent` must not have gets an identity of its own: the Playwright MCP server runs as `browsermcp`, the one user beside root that may reach the browser's debugging port, and the X clients of computer use and of the Browser tab run as `desktop`, the one user beside `browser` that may read the X authority file. A spawn request names the identity in `identity`, and `resolveExecutable` takes the same name for its `PATH`. The name comes from the caller's own config row (`dsh-computer-use-x11` `identity`, `@mumbo/box-links` `browser.identity`, the browser MCP providers' `identity`, which `dsh-mcp-client` passes on for a stdio server), never from model input; each identity has its own environment and secret names; a name the provider does not list, or any name without `runAs`, is refused before anything starts, and `dsh-subprocess-ssh` refuses every name. A stdio MCP server with an `identity` starts through `ctx.subprocess` instead of the MCP SDK's own spawn, with the identity's environment plus its configured `env`, in that identity's own home, never in a Session working directory, where the model could plant the code or configuration the server reads. `ctx.subprocess.serverHome(identity)` returns that home once `dsh-subprocess-local` has checked the entry by the server identity's rules below, so its `PATH` and `NODE_PATH` name no directory the model can write; mcp-client fails such a row at load when the check fails, and fails a `cwd` naming another directory. In a person box `browsermcp`'s home is `/home/browsermcp`, and its groups hold only `uploads`, for the copies browser consent stages, never `shared` or the workspace's group. `@mumbo/browser-consent` gives the server its `uploadStaging` directory as its only MCP root, so the server's workspace is no Session directory, and it requires `browser.outputDir` and deletes a withheld result's files only there.
- **MCP server identity.** The servers a person adds through `dsh-mcp-manager` hold the person's credentials (`${credential:…}` in their `env`), which must not sit in the uid whose shell the model drives. So under a provider with a run-as identity, a stdio MCP server that names no identity, every manager entry included, starts through `ctx.subprocess` as the provider's `serverIdentity`, the box's `mcpserver` user, never as root or `agent`; an entry has no identity field, so it cannot select another identity or root, and a provider that names no server identity fails the server instead. It starts in that identity's home, never in a Session working directory or `dsh`'s own, and an entry `cwd` naming anything else fails it. Its environment is the entry's `env` over the identity's base, which in a box is only `HOME`, `USER`, `PATH` and `LANG`; the box secrets stay in `secretNames`, so an entry naming one fails with the provider's refusal. A credential belongs in `env`, which `/proc/<pid>/environ` shows only to the same uid and root: every uid can read a process's command line through `/proc/<pid>/cmdline`, so under a run-as provider mcp-client fails a stdio server whose `command` or `args` references a credential before it resolves any, with a message that points to `env`. The harness does not rely on the box mounting `/proc` with `hidepid=2`. At load `dsh-subprocess-local` requires the server identity's `set.HOME` to be its real path, owned by that identity and writable by no other user but root, directly or through an ancestor, and searchable by it, and requires `set.PATH`, which callers cannot replace; every `PATH` and `NODE_PATH` entry the identity receives, at load and again at each spawn, must be a directory that only root can change along both its spelling and its real path, so no model-writable directory can supply the code the server runs. `mcpserver` has no `shared` group and no route to the browser's debugging port. Whether it reaches the workspace is the box's `mcpServerWorkspace` switch (`none`, the default, `read` or `readwrite`): the box applies it to the workspace's permissions and the edge expresses it as `identities.mcpserver.groups`, which the exec bootstrap sets exactly, so with `none` the list is empty and `mcpserver` holds no group that reaches a model root. For `read` and `readwrite` the list holds one dedicated workspace group that only the workspace's directories carry, to which the box gives group read or read-write access on `/root/projects`; never `agent`'s primary group 1001, which owns every `root:agent` `2750` directory (the attachment and spill stores, the subprocess spill directory, the superagent worker directory), and never `shared`. The model roots give `other` no permission bits, so without that group `mcpserver` reads none of them. mcp-client decides at each connection from the provider mounted then, so a box's `dsh-mcp-manager` row declares `inject: [credentials, subprocess]`: Cordis runs it only while a subprocess service is mounted, so after a provider remount, or when the provider failed at load, no server starts at all rather than as root. The row's `config` cannot carry such a switch, because a launch patch replaces a row's whole `config` after the person's settings layer and would erase the servers the person added. A start the provider refuses, such as an entry `env` naming a `secretNames` variable, fails with the provider's refusal, which names the variable, and confirms closure, so the entry can be fixed and restarted without a Host restart.
- **Computer use arguments.** The model chooses coordinates, keys and text, so `dsh-computer-use-x11` checks the whole `xdotool` argument list before every start: it must parse as the commands the provider sends, with decimal numbers, buttons 1 to 7, and key names from the closed set, and typed text is only the final argument after `type --`. No model-derived argument can start another `xdotool` command such as `exec`, which would run a program as `desktop`.

### Model roots on the filesystem provider

`@deepseek-ai/dsh-fs-local`, and through inheritance `@deepseek-ai/dsh-fs-sandbox`, takes `modelRoots`, a list of existing absolute directories canonicalized at load:

```yaml
- id: fs-sandbox
  name: '@deepseek-ai/dsh-fs-sandbox'
  config:
    modelRoots: [/root/projects, /home/agent]
```

- The `FileSystem` Service Definition gains `resolveModelPath(path, opts)`. Every model-facing tool resolves model-supplied paths through it: `read` and `read_image` (shared read-target step), `write`, `edit`, `apply_patch`, `str_replace_editor`, `present`, the `glob` and `grep` search root (or the working directory when no path is given), and the LSP host's query source. With roots configured, the local provider walks the path one name at a time from `/`, following links and `..` as the kernel does, refuses with `FS_OUTSIDE_ROOTS` before it examines a name that is neither under a root nor an ancestor of one, and refuses a walk that ends outside every root; an absent path ends at its first missing name, so a write target under a symbolically linked parent is judged by where it would land. The model reads `cannot access "<path>": its real path is outside the directories you can access (<roots>)`.
- Every `resolve` call, not only model-facing ones, refuses a path written under a root whose real path leaves all roots. The model can create symbolic links anywhere under its roots, so harness readers of model-writable directories (project instruction files, workspace skills, the Files panel) never follow such a link out. Paths outside the roots that no root contains, such as the harness's own `DSH_HOME`, resolve as before.
- The allowlist is not a denylist: the file tools run in the root `dsh` process, which can read `/proc/<pid>/environ` of any process and every root-only file, so only an explicit set of directories is safe. Shared temporary directories stay out of it for the same reason: every file under a root is readable to the root process whoever owns it. Model roots require Linux.
- **Reads are pinned to the resolved file.** Every read and listing opens its target once (`O_NONBLOCK`) and accepts the descriptor only when `/proc/self/fd/<n>` names the resolved real path, then reads through that descriptor; listings read names and children through it too. A link swapped in after resolution is refused (`FS_OUTSIDE_ROOTS` when the opened file lies outside the roots, `FS_STALE_VERSION` otherwise).
- **Harness readers and the Files panel.** A planted link out of the roots reads as absent in instruction and skill discovery. The Files panel resolves with `unconfined: true` and opens files through such links as before. Because the walk never examines a name outside the roots, a path through one gets the same refusal whatever exists there, so the model learns neither existence nor type: a name behind a planted link, a `..` that would come back into a root only if the outside directory exists, and a final link to a missing or an existing outside file. One walk decides where a path leads and how it fails, and it examines each name within a descriptor of the directory it holds, never by a path the kernel would walk again, so a link the model's shell repoints, or a directory it swaps for a link between two steps, changes only which way the walk goes; a resolution that checked the path in one walk and resolved it in another, or that looked a name up again from the root at each step, would let such a race reveal what it saw outside. `present` resolves before it inspects a path.
- **Working directories.** A directory the model chooses, through `working_directory` or a subagent's `cwd`, resolves through `resolveModelPath`, so one outside the roots is refused. The Session's original project is the person's choice and stays unconfined, and so does a directory the person or the harness sets later, such as one an SDK client sets or a subagent directory a workflow derives: `set` records it with `chooser: 'host'` on its `working-directory/change`, also when it sets the directory already recorded as the model's, and a subagent that inherits its parent's directory inherits its chooser. A working directory never extends the roots: a Session whose directory lies outside them, such as a host-chosen origin, still has file tools that reach only the model and read-only roots, relative paths resolved against that directory included. A model-chosen directory outside the roots is not followed: `ensure()`, which instruction and skill discovery call before they read, returns to the original project through a logged `working-directory/change` and the existing notice, so the model sees no directory change that the Session log does not record. An event without `chooser`, including every event written before the field existed, counts as the model's choice, because confining a directory of unknown origin costs at most a logged return to the original project, while following one could load a planted instruction file into root `dsh`. A host-chosen directory under a root whose real path now leaves the roots is not followed either. Without this, the model's shell could plant an `AGENTS.md` link to a root-only file in a directory outside the roots and move the Session there, and root `dsh` would load the file into the next request. Subagent start requests carry `cwdChooser`; a caller that derives the directory itself, such as a workflow, passes `'host'`, and the child's log records it. A listing reports a child whose real path leaves the roots as an opaque `other` entry. Under a run-as provider, a hard-linked regular file the run-as user does not own is refused on read. `fs-local` refuses model roots that contain `os.tmpdir()`.
- **Changes run as the run-as user.** The subprocess Service Definition exposes `childIdentity`. When it is set, every `ctx.fs` change (write, edit, patch, delete, move, directory creation) runs in a one-shot helper process (`@deepseek-ai/dsh-fs-local/mutation-helper`) that the run-as provider starts, using the provider's own in-process implementation, so the kernel checks every path component of the change with the run-as identity and a swapped link cannot lead a change outside what that user may write. The parent keeps its per-target locks, decodes the helper's output strictly, and maps its failures back to their filesystem codes. With model roots and no subprocess provider mounted, changes are refused instead of made by root.
- The person's Files panel resolves through plain `resolve` and its own workspace containment, so it is unchanged except that it, like every caller, no longer follows a link out of the model roots.
- **Read-only roots.** The harness names some of its own directories to the model: an uploaded file's read-only copy in the attachment store, a skill's base directory under `$DSH_HOME/skills` or `$DSH_AGENTS_HOME/skills`, and spill paths. `readOnlyRoots` lists exactly those directories beside `modelRoots`; reads and listings under them follow every model-root rule, and every change under them is refused with `cannot <verb>: it is in a directory you can only read (<roots>)`. The attachment store keeps hard-linked names, so the link-count rule does not apply under read-only roots; that is sound only because the run-as user cannot write there, so read-only roots may not overlap model roots. A read-only root that is or contains `$DSH_HOME`, or that is, contains, or lies inside a conventional credential store under the home directory, fails at load. These roots open files to root's `read` only. The model's shell needs the same files, for example a binary upload for bundled Python or a skill's scripts, so the box moves them out of the root-only harness home into directories the run-as user can read but not write: `dsh-attachment-local` `dshHome: /var/lib/mumbo/attachments` and `dsh-spill-local` `root: /var/lib/mumbo/spill`, both with `groupReadable: true` (directories `2750` or `0750`, files `0440` or `0640`) under a `root:agent` set-group-ID home, the provider's `spillDirectory`, and skills under `DSH_AGENTS_HOME=/usr/local/share/mumbo/agents` (root, world-readable). The file tools themselves were not widened: no copy path from a read-only root exists.

### Nothing model-reachable loads code into root dsh or starts a root process

`apps/cli/tests/box-containment.spec.ts` composes the person and project boxes (the web profile, the founder's overlays, the edge's rows, the door overlay `packages/mumbo/mcp/examples/person.overlay.yml` that the edge patches into person boxes, and the edge's containment rows in `apps/cli/tests/fixtures/box-edge`) and classifies every mounted package by how its model tools run: none, in-process, model roots, run-as, remote, or withheld. It also lists every subprocess identity a row names against its package, requires exactly the classified ones (`desktop` for computer use and the Browser tab, `browsermcp` for the Playwright MCP server) plus the provider's `serverIdentity`, `mcpserver`, and requires each to be a configured non-root identity distinct from `agent` and from each other; `mcpserver` holds no group `agent` or another identity holds, inherits only `LANG`, and sets only `HOME`, `USER` and `PATH`. A composition that mounts `dsh-mcp-manager` or a stdio `dsh-mcp-client` row naming no identity fails unless every subprocess provider row sets `runAs` and names `mcpserver` as its `serverIdentity`, and that row injects `subprocess`, because mcp-client starts such servers as root otherwise, so no MCP stdio server starts as root or as `agent`; the `@mumbo/superagent` orchestrator tools are listed by name and must equal the names of the tools its main and Executor Session builders (`mainTools`, `executorTools`) return, which are exactly the tools it registers, so a new one fails the gate until it is classified, whatever its name or wherever it is defined; the person box's `@mumbo/mcp` row must serve the `door` profile, whose tools must equal the names its `registerTools` registers for that profile, which is exactly what each request's server serves, the four data-only ones in process and `task_status` and `task_result`, which run git in `assistantCwd`, through the run-as provider as `agent`; no containment row patches `dsh-superagent`, whose config a patch would replace whole, so the project box's row is the founder's `deploy/mumbo-project.overlay.yml` row, which must read `workDirectory`, `workerDirectory` and `ghConfigDirectory` from `MUMBO_WORK_DIR`, `MUMBO_WORKER_DIR` and `MUMBO_GH_CONFIG_DIR`, which a contained project box's start script exports, and leave them unset without them; `browsermcp`'s groups must be exactly `uploads`; `web_fetch` must use the DeepSeek Fetch API (`deepseek-fetch-api`) with its base at the edge's model host's `/v1/tools`, where the composed `web` row differs from the base's only in its fetch provider, and the composed web rows booted through the Loader must send a fetch of a loopback URL to that host alone; the project rows must put the superagent's worker shims and git configuration into the run-as environment; no value of the subprocess row may name a path in `/root/.mumbo`, which stays `0700`, and the box layout under Consequences must name every model root, read-only root, and subprocess directory the rows require to exist. An unclassified package fails, catalogued tool names must match `docs/tool-catalog.md`, and `dsh-tool-cordis`, `dsh-plugin-market/tools`, the Python PTC runtime, the SDK subagent, and the anonymous fetcher `dsh-web-fetch-http` must be absent. `dsh-web-fetch-http` fetches from root dsh, outside the agent network rules, and reaches loopback and private addresses, such as the browser's debugging port and the box's own services; the containment rows disable it and point `dsh-web-deepseek-api` `fetchBaseURL` at the edge's model host, which forwards `/v1/tools/*` to DeepSeek with the box token. Two harness switches back the containment rows: `dsh-plugin-manager` `modelTools: false` keeps the `plugin_manager` tool from registering (installing or enabling a plugin loads code into root dsh), and `dsh-workspace-changes` `summaries: false` keeps change summaries from running git or reading files until their scratch directory works as the run-as user. The creator-mode preset (`preset-cordis`) is disabled.

## Alternatives considered

**A run-as field on each spawn request instead of a provider-wide default.** Each Consumer would declare whether its process acts for the model. It is explicit, but every current and future spawn path would have to opt in, the Consumers inside Agent Preset realms would each need the identity, and an omission would run as root silently. The provider-wide identity fails closed for new paths; the harness's credentialed processes already spawn outside the seam. Named identities are an addition for helpers that need other access, and an omitted name falls back to `agent`, never to root.

**Computer use as the host's own user.** `xdotool` needs the X authority file, which `agent` must not read because the display shows the person's signed-in browser. Running it as root or as `browser` would hand any `xdotool exec` to an account that reaches more than the desktop; `desktop` reaches only the display.

**Typed text through `xdotool type --file -`.** Standard input keeps the text out of the argument list, but the strict argument check is simpler to state and test when every model-derived value is an argument it can see; the text after `type --` is always the final argument, which `xdotool` types literally.

**`dsh`'s own sandbox (bubblewrap or Landlock).** It confines writes, not reads, applies per mode with user-approved escalation to Full access, does not cover the person's Terminal tab, and was unavailable on Fargate. A uid boundary holds regardless of mode and approval.

**Node's `spawn({ uid, gid })` and `node-pty`'s `uid`/`gid`.** They need no bootstrap, but `node-pty` keeps root's supplementary groups and neither can set an explicit group list.

**A wrapper program such as `setpriv`.** It would run as root with the target's environment, which the dynamic loader honors (`LD_PRELOAD`), and adds an external dependency. The bootstrap keeps the target environment in a root-only request file and runs with `dsh`'s own scrubbed environment until it has dropped privileges.

**Strict allowlisting of explicit environment entries too.** It would make a forwarded secret impossible under any name, but it silently drops Consumer facts that correctness depends on (`GIT_INDEX_FILE` in change capture would make git write the user's real index). The secret guard covers named secrets instead.

**Enforcing model roots in every `resolve`.** It would cover any future model tool without an opt-in, but it would break harness reads of `DSH_HOME` (global instructions, skills, spill files) and change the Files panel. Only the symbolic-link escape rule applies to every caller.

**A per-tool `tools/pre-execute` path filter.** Tool arguments name paths in different fields and forms, and a filter before resolution cannot see symbolic links; enforcement belongs at the resolution that produces the target.

## Consequences

- With both settings, a model-driven process cannot read root-only files or other users' files, cannot read `/proc/<pid>/environ` of root processes, and starts without the box credentials; the model's file tools cannot name a path outside the roots or follow a link out of them.
- `dsh` itself still runs as root. A flaw in `dsh` or in any in-process plugin, or a harness process that interprets model-writable content as root, reaches everything. The composition gate keeps model tools that load code or start root processes out of the box compositions. The superagent orchestrator's own `gh` and Feishu CLI calls stay root by design; they run a root-owned CLI with a root-owned `GH_CONFIG_DIR` in `/`, never in a ticket directory, and run no git. Without `modelTools: false` the plugin-manager tool installs and enables bundles in the root process without approval under Full access.
- Reads are pinned to the resolved file and changes run as the run-as user, so a link swapped in during a tool call can neither be read through nor written through outside the roots. Without a run-as provider, changes still open the canonical path by name in the root process and keep that race. Each change costs one helper process start (about 0.3 s from source).
- Every MCP server the person adds runs as the one `mcpserver` user, so each can read the others' environments and files, credentials included. The model reaches that uid through the servers' own tools: a server whose tools write files or run commands, such as a filesystem server working in its home `/home/mcpserver`, where `npx` keeps the packages other entries start from, lets the model place code that runs as `mcpserver` at another entry's next start, and that code reads every panel server's credentials. The servers get no private temporary directory, so they share the world-writable `/tmp` with `agent`, which can plant files at names a server predicts there. A panel server that writes files or runs commands therefore hands the model every panel credential. A user per server, and a private `/tmp` for `mcpserver`, are later options.
- Run-as children need read access to `dsh`'s own code for the PTC runtime and the file-change helper, and to any executable they run; `dsh`'s source tree, `node_modules` and `DSH_HOME` must stay unwritable by the run-as user, or it can change code that root executes.
- Box layout the rows depend on. `fs-local` realpaths every model and read-only root at load and `subprocess-local` checks its two directories at load, so each directory the rows name must exist before dsh starts: the model roots `/root/projects`, `/home/agent` (with the run-as `TMPDIR` `/home/agent/tmp`), and `/home/shared/Downloads` in person boxes or `/root/work`, owned by `agent`, in project boxes; the read-only roots `/var/lib/mumbo/attachments/attachments/v1`, `/var/lib/mumbo/spill`, `/var/lib/mumbo/subprocess-spill`, `/root/.dsh/skills`, and `/usr/local/share/mumbo/agents/skills` (root, `0755`); `/run/dsh-shell` (root, `0711`); and dsh's own `TMPDIR` `/root/.dsh/tmp` (root, `0700`, named by its real path). Project boxes also need the superagent's worker directory `/var/lib/mumbo/superagent` (`root:agent` `2750`, with `worker-bin` `2750`, shims `0750` and `worker-gitconfig` `0640`, which dsh-superagent writes; the main orchestrator Session starts there) and the orchestrator's `GH_CONFIG_DIR` `/root/.config/gh` (root, `0700`, signed in to the agent's GitHub account, which setup reads the agent's login from), each root's with no group or other write anywhere on the path, or the plugin fails at load; the agent GitHub CLI the panel names, such as `/usr/local/lib/mumbo/bin/gh`, is root's with no group or other write on its path, or setup refuses it. `/var/lib/mumbo` is `0755`; `/var/lib/mumbo/attachments`, `/var/lib/mumbo/attachments/attachments`, `/var/lib/mumbo/attachments/attachments/v1`, `/var/lib/mumbo/spill`, and `/var/lib/mumbo/subprocess-spill` are each `root:agent` `2750`. The attachment store creates `attachments/v1` only on its first upload, so the box creates it. `/root/.mumbo` stays `0700`, so the project rows put the `gh` wrapper on `PATH` from `/usr/local/lib/mumbo/bin` and point `NODE_EXTRA_CA_CERTS` at `/usr/local/share/ca-certificates/mumbo-box.crt`, both root-owned and world-readable. The host has `fs.protected_hardlinks=1`. Person boxes need `browsermcp`'s home `/home/browsermcp` (`browsermcp`, `0700`, under root-owned `/home`, with every directory on its `PATH` root's), the Playwright MCP output directory `/var/lib/mumbo/playwright-output` (`browsermcp`, `0700`, outside backups), which `browser.outputDir` names, and browser consent's staging directory `/var/lib/mumbo/uploads` (`root:uploads` `2750`, emptied at every start, outside backups), which `uploadStaging` names, with the group `uploads` holding `browser` and `browsermcp` alone. Both boxes also need the `mcpserver` user (uid and gid 1006, in no other group while `mcpServerWorkspace` is `none`) and its home `/home/mcpserver` (`mcpserver`, `0700`, under root-owned `/home`), and every directory on its `PATH` (`/usr/local/bin`, `/usr/bin`, `/bin`) owned by root and writable by no group or other user. The model roots give other users no access (no `other` permission bits), so `mcpserver` reaches no Session working directory unless `mcpServerWorkspace` grants it the workspace group.
- The edge's person-box consent row must carry `uploadDirectory: /home/shared/Downloads`, its real path below root's `0755` `/home/shared` and `/home`, `uploadStaging: /var/lib/mumbo/uploads`, and a `browser.outputDir` that `browsermcp` owns. Without them `@mumbo/browser-consent` fails at load, and computer use, whose row injects the consent service, does not load either. An edge that picks the consent row by probing the harness probes for `uploadDirectory` and `uploadStaging`, because harnesses that do not require them also accept `deniedUrls`. `uploadMaxBytes` keeps its default, 512 MiB.
- Harness-initiated work that now runs as the run-as user needs paths that user can use: workspace change capture keeps its scratch index under a root-owned `0700` temporary directory and fails under run-as until it creates that scratch for the run-as user; superagent workers read their shims and git configuration from the worker directory, which the run-as environment names, because they do not receive dsh's own environment. Under run-as the main orchestrator Session starts in that worker directory, which `agent` can enter but not write, so root never reads instructions or skills a worker planted, such as an `AGENTS.md` in the work directory; its preset has no `working_directory` tool to leave it. A project box that ran dsh-superagent before the containment rows keeps its main Session and, by default, its ticket directories in the root-only state directory: the main Session's id under run-as names the worker directory, so a new one starts there and the earlier one keeps its history, and a Ticket whose directory is in the state directory fails at its next launch, before anything runs, saying that its files stay there and a new Ticket must take the work. The box finishes or stops live Tickets before it gets the containment rows.
- Under model roots a Session keeps a working directory outside the roots only when its log records that the person or the harness chose it; a Session whose log predates the `chooser` field returns to its original project from such a directory on its next request.
- Each run-as launch starts one extra Node bootstrap before `execve`, which systemd-scoped launches already paid.
- Credential-dropping cannot be exercised by a non-root test run. The suites run the bootstrap with the test's own identity, prove a different identity is refused, and assert the request and argv the provider produces; the box's escape tests run as the real `agent` user.
